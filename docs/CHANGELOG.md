### 2026-08-17 — Added: ошибки и отчёты в форум-темы по режиму (OTC/FIN) вместо плоских каналов
- **`settings/logger_config.py`.** Адрес назначения логов теперь пара `(chat_id, thread_id)`:

  + `MESSAGE_TOPIC_OTC`/`MESSAGE_TOPIC_FIN` для REPORT-отчётов. Тема выбирается по `BINARY`, так
  что FIN и OTC не мешаются в одной ленте. Форумы РАЗНЫЕ: рабочий поток отчётов не должен топить

  ценности не имеет — переносить есть смысл только вместе с решением, что с ним делать.
- **`session_dest` без `SESSION_CHANNEL` теперь следует за ошибками** (включая форум-тему). Иначе
  после переезда ошибок единственный критичный алерт об отвале session остался бы в опустевшем
  канале, куда никто больше не смотрит.
- **`logs/log_init.py`.** `_send_message` принимает `thread_id` и передаёт `message_thread_id`
  (для канала — None, aiogram параметр опустит).
- **Проверено оффлайн:** BINARY=0 → тема OTC, BINARY=1 → тема FIN, без `ERROR_FORUM` → старый
  канал, `SESSION_CHANNEL` перебивает наследование адреса ошибок.

- **`apps/binodex_feed.py`.** После первого признака жизни `wait_for_feed` больше не возвращает
  `True` сразу: сначала `confirm_stable` держит binodex под наблюдением `FEED_CONFIRM_WINDOW`=60с.
  В окне параллельно следим за ДВУМЯ сервисами — market-WS должен слать тики нашей пары без пауз
  длиннее `FEED_CONFIRM_GAP`=3с, auth-API обязан оставаться не-5xx на перепроверках раз в 20с.
  Срыв любого → назад в ожидание, «вверх» НЕ рапортуем (в файл — `warning`, без TG-спама).
- **Критерий непрерывности перенят у `BinodexScreens._probe_stable`** (STABLE_GAP=3.0), где защита
  от мигания проверена на живом фиде. Отличия намеренные: окно меряем в секундах, а не в числе
  тиков, и параллельно проверяем auth-API — у Screens гейт фид-онли, и ровно этим он 16-08
  пропустил волну (фид жил, `api.binodex.app` отдавал 503 MAINTENANCE).
- **Тики фильтруем по своему символу** (`want` в `_frames`): живой соседний тикер не должен
  маскировать молчание нашей пары.
- **Грабли asyncio (стоили бы зависшего стопа).** `asyncio.wait_for` в 3.11 ГЛОТАЕТ отмену, если
  внутренний future успел завершиться. Тики идут по несколько раз в секунду, поэтому `cancel`
  почти всегда приходится ровно на этот момент: наблюдатель `_watch` не отменялся и досиживал
  всё окно (в тесте — 10с при cancel на 0.1с, `cancelled=False`). Поэтому наблюдатели
  останавливаются явным общим флагом `abort`, а не отменой таска.
- **Проверено оффлайн (9 сценариев, без сети и БД):** ровный поток выдерживает окно; пауза больше
  gap рвёт; обрыв сокета рвёт; чужие символы не наращивают серию; 503 API внутри окна → False;
  срыв фида роняет подтверждение не досиживая окно; `stop_event` прерывает окно за 0.1с вместо 10;
  две «вспышки» подряд отброшены, `True` только с третьей, устойчивой.

### 2026-08-15 — Fixed: порванный аплоад (FILE_PART_*) больше не стоит рестарта юнита
- **`apps/my_exeptions.py` `lost_connection_photo`.** Если media-соединение умирает ПОСРЕДИ
  загрузки файла, pyrofork это наверх не поднимает: воркер в `save_file` глотает ошибку `invoke`
  (`log.exception`), аплоад «завершается» с недостающими частями, и отправку отбивает уже сервер —
  `FILE_PARTS_INVALID` / `FILE_PART_X_MISSING`. Такая ошибка падала в общую ветку внизу, то есть
  пост терялся, а цикл уходил в `exit_main(fall=True)` → рестарт юнита с переподъёмом Firefox.
- **Теперь** это отдельная ветка: один повтор отправки (`save_file` возьмёт новый `file_id`, а
  media-сессия уже выброшена `ReusableMediaSession.invoke` на ошибке связи и поднимется заново).
  Пробы доставки здесь НЕ делаем — как и у FloodWait: сервер ОТКЛОНИЛ отправку, сообщения в канале
  нет, дубля повтор не даст. Не вылечилось повтором → штатный провал без эскалации транзиент-401.
- **Почему это не теория.** На проде (node-2, 1m OTC на новом коде) соединение к media-DC
  пересоздаётся раз в 1.5–2 мин, на установленном потоке видны `retrans/lost/backoff` — попасть
  серединой аплоада в разрыв это вопрос времени, а не редкая экзотика.
- Маркер ловим подстрокой `FILE_PART` в тексте ошибки: pyrofork отображает в классы лишь часть
  кодов (напр. `FILE_PART_0_MISSING`), остальные приходят общим `BadRequest` с кодом в тексте.
- **Проверено оффлайн (5 сценариев):** FILE_PART → повтор и успех; `FILE_PARTS_INVALID` ловится
  тем же маркером; пробы истории не происходит (даже когда в истории лежит свежий пост с тем же
  текстом — повтор всё равно уходит); двойной провал отдаёт `(False, текст, None)` без рестарта
  клиента; посторонняя ошибка (`PEER_ID_INVALID`) в эту ветку не попадает.

  переживался в релогине. Теперь один список маркеров и одна реализация; в список добавлены
  Chromium-эквиваленты (`ERR_CONNECTION_RESET`/`ERR_NAME_NOT_RESOLVED`/…) — OTC по умолчанию

  Инвалидировала ЛЮБАЯ ошибка `invoke`, а это работало против самого патча: pyrofork внутри
  `Session.invoke` сам ретраит сетевые сбои (`OSError`/5xx, до `MAX_RETRIES`=10) и отсыпается на
  FloodWait, поэтому наружу выходят в основном RPC-ошибки при ЖИВОМ соединении (`FILE_PART_*`,

  `(OSError, ConnectionError, TimeoutError, asyncio.TimeoutError, Unauthorized)`; остальное
  пробрасывается как есть, соединение живёт.

### 2026-08-15 — Разобрано при инциденте с SYN-фильтром: альтернативы, отвергнутые и отложенные
> Держим здесь, чтобы не пере-предлагать: по каждому пункту есть замер или названная цена.

- **`Client(alt_port=True)` (порт 5222 вместо 443) — ОТВЕРГНУТ замером.** Гипотеза была, что
  полисинг висит на 443-листенере и альтернативный порт не полисится. Замер с NODE-6 на media-DC
  `149.154.167.151`, 60 проб на порт: **443 — 20 потерь из 60 (33%), 5222 — 24 из 60 (40%)**; на

  пределах шума → дроп идёт **по адресу целиком, независимо от порта**. Технически патч сработал бы

    закрыться (тот же класс аварии, что при двойном запуске).

    слушание WS до возврата котировок, ОДНО уведомление вниз/вверх, без релогина/спама);
  - **WS жив, но пост не снять** → браузер-фри тут не годится (условие выхода «WS ожил» уже истинно →
    мгновенный возврат → петля пересоздания), поэтому держим браузер и делаем лёгкий повтор цикла

### Оптимизации

#### Исправления багов

**Race condition регистрации страниц** (`apps/browser_app.py`)
- Проблема: `handle_popup` закрывал новые страницы до регистрации
- Решение: страница регистрируется в `manager.pages` сразу после получения

**Busy loop в find_point** (`apps/app.py`)
- Проблема: `while` цикл без паузы нагружал CPU
- Решение: добавлен `await asyncio.sleep(0.1)`

### Маппинг API

| Selenium                                   | Playwright                       |
|--------------------------------------------|----------------------------------|
| `webdriver.Firefox(options)`               | `playwright.firefox.launch()`    |
| `driver.get(url)`                          | `page.goto(url)`                 |
| `driver.find_element(By.CSS_SELECTOR, s)`  | `page.locator(s)`                |
| `driver.find_element(By.ID, id)`           | `page.locator(f"#{id}")`         |
| `driver.find_element(By.CLASS_NAME, c)`    | `page.locator(f".{c}")`          |
| `driver.find_element(By.XPATH, x)`         | `page.locator(f"xpath={x}")`     |
| `WebDriverWait().until(EC.*)`              | Встроенные auto-wait             |
| `ActionChains().move_to_element().click()` | `locator.click()` / `page.mouse` |
| `element.screenshot(path)`                 | `locator.screenshot(path=path)`  |
| `driver.execute_script(js)`                | `page.evaluate(js)`              |
| `driver.add_cookie(cookie)`                | `context.add_cookies([cookie])`  |
| `driver.switch_to.new_window('tab')`       | `context.new_page()`             |
| `element.get_attribute("textContent")`     | `locator.text_content()`         |
| `element.value_of_css_property(p)`         | `locator.evaluate()`             |
| `element.send_keys(text)`                  | `locator.fill(text)`             |
| `driver.refresh()`                         | `page.reload()`                  |
| `driver.quit()`                            | `browser.close()`                |
